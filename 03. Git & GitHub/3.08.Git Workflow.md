# 📖 3.08. Git Workflow
Um **Git Workflow** é a forma como uma equipe organiza o trabalho utilizando Git e ferramentas como o GitHub.

Ele define, na prática, como as alterações são desenvolvidas, registradas, revisadas e integradas ao projeto.

Não existe um único workflow que precise ser utilizado por todas as equipes. O processo pode variar de acordo com o projeto e com as regras adotadas pela empresa.

## Fluxo Simples
Iremos utilizar apenas um fluxo simples para reunir os principais conceitos estudados até aqui.

No contexto de QA, o fluxo ajuda a incorporar a qualidade ao desenvolvimento das alterações.

Um exemplo completo seria:

```
QA recebe uma tarefa
        ↓
Cria uma branch
        ↓
Desenvolve ou atualiza os testes
        ↓
Executa os testes localmente
        ↓
Cria um commit
        ↓
Envia a branch para o GitHub
        ↓
Cria um Pull Request
        ↓
Revisão
        ↓
GitHub Actions executa os testes
        ↓
Alterações aprovadas
        ↓
Merge
        ↓
main
```
Esse fluxo utiliza os recursos estudados nos tópicos anteriores e permite separar o desenvolvimento das alterações da integração com a branch principal.

### 1. Atualizar o repositório
Antes de iniciar um novo trabalho, verifique se sua branch está atualizada com o repositório remoto.

Dependendo do fluxo adotado pela equipe, isso pode ser feito com `git pull` ou utilizando `git fetch` seguido da estratégia de integração definida pelo projeto.

### 2. Criar uma Branch
Em vez de realizar alterações diretamente na `main`, podemos criar uma branch específica para o trabalho.

```
git switch -c test/login
```

Nesse exemplo, a branch `test/login` será utilizada para trabalhar nos testes relacionados ao login.

O uso de branches permite manter diferentes linhas de desenvolvimento separadas.

### 3. Realizar as alterações
Depois de criar a branch, o trabalho pode ser realizado normalmente.

Em um projeto de QA, isso pode significar:

- adicionar testes;
- corrigir testes existentes;
- atualizar documentação;
- adicionar arquivos de configuração;
- realizar outras alterações relacionadas ao projeto.

Durante o desenvolvimento, podemos verificar o estado dos arquivos utilizando:

```
git status
```

### 4. Executar os testes
Antes de enviar as alterações para o repositório remoto, é importante verificar se o trabalho realizado está funcionando como esperado.

Em um projeto de automação, por exemplo, podemos executar os testes localmente antes de criar o Pull Request.

```
Alterações
    ↓
Testes locais
    ↓
Resultado
```

Essa etapa ajuda a identificar problemas antes que as alterações sejam compartilhadas com o restante da equipe.

### 5. Criar um Commit
Depois de verificar as alterações, podemos adicioná-las à Staging Area:

```
git add .
```

E criar um commit:

```
git commit -m "Add login tests"
```

O commit registra as alterações no histórico do repositório. O Git utiliza commits para registrar versões do trabalho realizado.

### 6. Enviar a Branch para o GitHub
Depois do commit, podemos enviar a branch para o repositório remoto:

```
git push -u origin test/login
```

Assim, a branch criada localmente também estará disponível no GitHub.

O `git push` é utilizado para atualizar branches remotas com commits locais.

### 7. Criar um Pull Request
Depois de enviar a branch para o GitHub, podemos criar um **Pull Request** para propor a integração das alterações na `main`.

```
test/login
     │
     │ Pull Request
     ↓
   main
```

O Pull Request permite revisar as alterações, discutir possíveis problemas e acompanhar o processo antes da integração.

### 8. Executar o GitHub Actions
O GitHub Actions pode ser configurado para executar automaticamente tarefas quando determinados eventos acontecem no repositório.

Por exemplo, um workflow pode ser executado quando um Pull Request é criado ou atualizado.

Em um projeto de QA, podemos utilizar esse processo para executar testes automatizados:

```
Pull Request
      ↓
GitHub Actions
      ↓
Executar testes
      ↓
Passou / Falhou
```

Dessa forma, os resultados dos testes podem fazer parte do processo de revisão antes do merge.

### 9. Revisar e integrar as alterações
Depois que as alterações forem revisadas e as verificações necessárias forem concluídas, o Pull Request pode ser integrado à branch de destino.

O merge integra as alterações de uma branch à branch atual.

O fluxo fica:

```
feature branch
      ↓
Pull Request
      ↓
Review
      ↓
Automated Tests
      ↓
Merge
      ↓
main
```
