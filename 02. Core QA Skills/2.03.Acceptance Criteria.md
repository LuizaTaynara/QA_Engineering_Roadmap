# 2.03. Acceptance Criteria
Os **Critérios de Aceite** são condições que definem quando uma funcionalidade pode ser considerada concluída e aceita pelo negócio. Eles descrevem o comportamento esperado do sistema e servem como referência para o desenvolvimento, os testes e a validação da User Story.

Critérios de aceite claros ajudam a reduzir ambiguidades, alinhar as expectativas da equipe e facilitar a verificação dos requisitos.

Os critérios de aceite têm como objetivo garantir que todos os envolvidos no projeto compartilhem o mesmo entendimento sobre o resultado esperado para uma funcionalidade.

Além de orientar o desenvolvimento, eles servem como base para a criação de cenários e casos de teste.

## Características de bons critérios de aceite
Os critérios de aceite devem ser:
- Claros e objetivos.
- Específicos e sem ambiguidades.
- Testáveis.
- Alinhados aos requisitos da User Story.
- Escritos de forma que permitam verificar se a funcionalidade foi implementada corretamente.

## Exemplo
### User Story
**As a** registered customer, **I want** to recover my password, **so that** I can access my account if I forget my credentials.

### Acceptance Criteria
- O usuário deve conseguir solicitar a recuperação da senha utilizando um e-mail cadastrado.
- O sistema deve enviar um e-mail com as instruções para redefinição da senha.
- Um e-mail não cadastrado deve exibir uma mensagem apropriada.
- O link de recuperação deve expirar após o período definido pela aplicação.

## O papel do QA
O QA revisa os critérios de aceite para verificar se estão claros, completos e testáveis antes do início do desenvolvimento. Quando identifica ambiguidades, cenários ausentes ou informações inconsistentes, busca esclarecimentos com o responsável pelos requisitos ou com a equipe do projeto.

Os critérios de aceite também servem como base para a elaboração dos cenários e casos de teste, contribuindo para que a funcionalidade seja validada de forma objetiva.

>💡Muitos materiais afirmam que os critérios de aceite **são escritos pelo QA**, mas isso não é uma regra. Na prática, eles podem ser definidos pelo **Product Owner**, **Business Analyst**, **cliente** ou pela **equipe** durante o refinamento, dependendo da metodologia adotada pela organização.
