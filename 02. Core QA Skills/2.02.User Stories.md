# 2.02. User Stories
As **Histórias de Usuário** são uma forma simples e objetiva de descrever uma funcionalidade sob a perspectiva do usuário. Elas ajudam a equipe a compreender a necessidade do usuário e o valor que determinada funcionalidade deve entregar.

As User Stories são amplamente utilizadas em metodologias ágeis, especialmente no Scrum, para representar itens do Product Backlog.

## Estrutura
Uma User Story *normalmente* segue o formato:

**As a** *[tipo de usuário]*, **I want** *[funcionalidade]*, **so that** *[benefício ou objetivo]*.

Essa estrutura ajuda a manter o foco no usuário e no valor da funcionalidade, em vez da solução técnica.

**Exemplo:** <br>
**As a** registered customer, **I want** to recover my password, **so that** I can access my account if I forget my credentials.

>💡 Esse é um formato amplamente adotado, mas não é obrigatório. Existem equipes que utilizam outros modelos de escrita de User Stories. O mais importante é que a história comunique claramente **quem é o usuário, qual necessidade deve ser atendida e qual valor será entregue**.

## Características de uma boa User Story
Um dos critérios mais conhecidos para avaliar a qualidade de uma User Story é o modelo **INVEST**, proposto por Bill Wake.

| Critério        | Descrição                                                          |
| --------------- | ------------------------------------------------------------------ |
| **Independent (Independente)** | Deve ser, sempre que possível, independente de outras histórias.   |
| **Negotiable (Negociável)**  | Pode ser discutida e refinada pela equipe.                         |
| **Valuable (Valiosa)**    | Deve gerar valor para o usuário ou para o negócio.                 |
| **Estimable (Estimável)**   | Deve permitir estimativas de esforço.                              |
| **Small (Pequena)**       | Deve ser pequena o suficiente para ser desenvolvida em uma Sprint. |
| **Testable (Testável)**    | Deve ser possível verificar se foi implementada corretamente.      |

O modelo INVEST auxilia a equipe na criação de histórias mais claras e de melhor qualidade.

## O papel do QA
O QA participa da análise das User Stories para verificar se elas estão claras, completas e testáveis. Durante o refinamento dos requisitos, o QA pode identificar ambiguidades, levantar cenários que não foram considerados e colaborar com a equipe para garantir que a funcionalidade possa ser validada de forma objetiva.

Como já vimos, quando necessário o QA esclarece dúvidas com o responsável pela definição dos requisitos ou com a equipe do projeto antes do início do desenvolvimento.
